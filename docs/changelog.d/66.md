### 25 Nov 2026 — The drift monitor takes its detector settings as one value (#66)
- **Changed** `score_batches` takes a `DetectorConfig` and a separate validation `threshold` (PR-E4), in place of eight keyword arguments that mirrored its fields. `run_drift` passes its `DriftConfig`, whose extra fields `f1_drop`, `drop_run` and `event` are lead-rule settings and carry no labels (PR-R2). One read-only table, `DETECTORS` in `drift/monitor.py`, holds each detector's name, scorer, flag field and two plain-words descriptions. `run_score` copies the descriptions into each health `detectors` entry, and `report/html.py` reads them from there, so its `DETECTORS` dict is gone. The two call sites no longer rename the config's `ks_frac` to a `ks_frac_flag` keyword.
- **Changed** (output) each `detectors` entry in `*_health.json` gains two description strings, `compares` (what the detector compares) and `means` (what a flag means). The page and the other outputs are unchanged.
- **Changed** the coupling rule in design §3.2 and `CLAUDE.md` now says every component depends only on `types.py` and `config.py`, neither of which imports from the package.
- **Tests** (`tests/test_drift.py`): the `FLAGS` copy is gone. Its `alert_flag=0.2` differed from the 0.5 default. `test_no_detector_accepts_labels` also checks that no `DriftConfig` field (which includes every `DetectorConfig` field) is named `y` or mentions `label`, because a parameter-name check goes blind once the settings are one value. The drift end-to-end test checks that the detectors receive the run's `DriftConfig`, equal to the one validated from the config dumped before the run, and only `threshold` as a keyword. `tests/test_score.py` checks that the health check receives the score config's `health` settings, copied at the call and equal to the ones validated from the config dumped before the run, and that every detector's score, flag level and flag in the health file and on the page match a health check the test runs before the run starts (before, only the alert-rate entry was recomputed). That check, and the alert-rate entry's own recompute, use the config's `reference` when it is set. It also checks the two description fields.
- **Rows** (`tests/test_integrity_mutants.py`): the planted-bug rows that pinned the old call sites (`FLAGS_AT_TEST`, `HEALTH_SITE`, `SCORE_ARGS`, the `run_drift` threshold site and the `DETECTOR_ROW` rows) are re-pinned at the new `score_batches(..., cfg, threshold=...)` call and the new health row. The alert flag level derived from test F1 row, which the issue's list missed, now plants `cfg.drift.model_copy(update={"alert_flag": ...})` at the `run_drift` call. A new row plants the score path's health-check settings with a flag level derived from test F1 (`cfg.health.model_copy(...)`), the match of the drift row, which the score path never had, another plants a KS level derived from test F1 with calibration left on, and a third sets that KS level on `cfg.health` before the call and restores it after. Three more plant a test-F1 KS level by routes that bypass the call: a second health check the health file is written from, the score path's detector table rebound for the call, and the page's KS row alone. A further row adds a second KS row to the page, which the test catches because it compares the page's whole detector table body, in order, as one string; another breaks that extra row across lines, and a third puts a KS table into the page's batch field. `report/html.py` now escapes the batch in the page's title and heading, as it does every other text field, and the test checks the exact title and heading. `DETECTORS` is a `MappingProxyType`, so a run cannot swap a scorer in place for the drift test's recompute to inherit, and `test_no_detector_accepts_labels` checks that it refuses. No row plants that swap: it now raises a `TypeError`, and the harness counts only an assertion failure as caught. Design §3.7 lists the settings check and these rows. None is dropped or excused.
- **Changed** design §3.7 and `.claude/agents/integrity-auditor.md`: a finding needs a plausible mistake. Code written to defeat a guard (a builtin or `DataFrame` subclass that changes how a value formats or renders, or a module function or table rebound at run time) is out of scope. The page-only routes of that kind found in the audit go undetected on `main` too, and are filed as #103.
